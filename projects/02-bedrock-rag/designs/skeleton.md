# Skeleton — AWS-native RAG

Design session, 2026-09-30. Covers slices 1–3.

## Problem

Project 01 hand-builds a RAG pipeline: `text_splitter`, `embedding_model`,
`vector_store`, `retriever`, `reranker`, each a component we wrote and can read.
Project 02 asks what changes when a managed service owns all five — what it costs
in control, in accuracy, and in what can still be measured.

The second purpose is learning. AWS is the subject, not just the host, which is
why the design prefers AWS's own mechanisms over clever ways around them.

## Scope

**In:** the write path (S3 → `data_source` → `ingestion_job` → `knowledge_base`),
the read path (`Retrieve` → `answerer` → answer), and the apparatus that produces
a benchmark number comparable with project 01's.

**Out, deliberately, each with its own session later:** reranking, the
OpenSearch Serverless hybrid-search spike, corpus expansion and its benchmark,
the upload/ingest/query API, and CloudWatch monitoring.

**Out permanently:** `RetrieveAndGenerate`. Retrieval and `generation` stay
separate so the `answerer` and its prompt remain ours and remain comparable with
project 01's. It is the obvious thing to reach for, and not reaching for it is a
decision rather than an oversight.

## Design

### The write path

`document`s land in an S3 bucket. A `data_source` points at that bucket through
the credential-free S3 connector and carries the chunking strategy. An
`ingestion_job` reads, chunks, embeds and stores into the `vector_bucket`.

There is **no `record_manager` and no Postgres**. A `knowledge_base` tracks what
it has already ingested, so a re-run syncs changes. That is one whole component
of project 01 that simply does not exist here, and it belongs in the comparison.

Chunking is `FIXED_SIZE`, `maxTokens: 250`, `overlapPercentage: 20`.

Bedrock chunks by **tokens, not characters**, so project 01's 1000-character
`CHUNK_SIZE` has no direct expression. 250 tokens is roughly 1000 characters of
English prose; the 20% overlap maps exactly. The translation is a guess, and it
is checked rather than trusted: after the first `ingestion_job`, the character
lengths of retrieved `chunk`s are compared against project 01's distribution.
No tokenizer probe first — one measurement after the fact beats an estimate
before it.

A mismatch remains that no setting closes. `RecursiveCharacterTextSplitter`
splits on a descending list of separators and produces variable-length chunks
that tend to respect prose boundaries. `FIXED_SIZE` cuts at token boundaries.
Project 02's chunks will be more uniform and less structurally clean. "Matched"
means close, never equivalent.

### The read path

One `rag_query` is a `Retrieve` call with `numberOfResults: 8`, then a `Converse`
call to the `answerer`. It returns the answer and its token usage together.

`numberOfResults: 8` matches project 01's shipped `TOP_K=8`. The prompt is `v1`,
verbatim — prompt alone moved `correct` from 0.840 to 0.960 in project 01, so it
is a first-order variable and slice 3 has to hold it fixed.

`maxTokens` is set explicitly on every `Converse` call. Leaving it unset reserves
the model's maximum against the account quota and is a common cause of surprise
throttling.

### How it is observed

The `rag_query` is `@traceable` into LangSmith, using project 01's evaluators and
the same 25-question benchmark. Nothing instruments boto3, so usage reaches the
`trace` only because the traced function **returns** it — the pattern project 01
already proved, where a `@traceable`'s return value is serialised into the trace
by construction. Unlike project 01, no private-method subclass is needed:
`Converse` hands back `usage` in its documented response.

The `trace` carries input and output tokens. It carries **no dollar cost**.
Bedrock returns no cost figure, so any dollar number would be computed by us, and
a computed number sitting in the same column as project 01's measured one is a
trap this repo has been caught by before. Dollars are handled separately through
Cost Explorer.

**Tokens are the cross-project metric.** Project 01 runs `deepseek-v4-flash` and
project 02 runs a Bedrock `foundation_model`; comparing their dollar costs
measures vendor pricing, not the two systems. Prompt tokens are set largely by
retrieval — how many `chunk`s of what size reach the `answerer` — so they compare
the pipelines honestly. Dollar cost stays a within-project lever, as it was for
`TOP_K=8`.

CloudWatch is a separate concern, in a later slice. LangSmith owns the
comparison; CloudWatch will own production monitoring.

### Configuration

The `knowledge_base` and `data_source` ids are generated by AWS, so they cannot
be committed defaults the way `DEFAULT_TOP_K` and `DEFAULT_QDRANT_URL` are.
Terraform writes them to SSM at committed paths, and the **path** becomes the
default — a constant in the code, with whatever the current stack produced behind
it. A fresh clone with AWS credentials works with no manual step, and the
parameters are in Terraform from the start rather than made by hand, which is a
loose end project 01 is still carrying.

The cost is real: `src/` now needs AWS credentials and a deployed stack to build
its config at all.

### Models

| | Project 01 | Project 02 |
|---|---|---|
| `embedding_model` | `baai/bge-m3`, 1024 dims | Titan Embed Text V2, 1024 dims |
| answering model | `deepseek-v4-flash` | Claude Haiku 4.5 |

Neither can be held constant, so **both are confounds in slice 3** and the
roadmap entry must say so. Slice 3 is never a clean "managed vs hand-built"
comparison; it is project 01's pipeline with deepseek against Bedrock's with
Claude.

Haiku 4.5 is chosen as the nearest class match to `deepseek-v4-flash` — small,
fast, cheap tier — so the confound is small rather than generational. Sonnet
would probably win and would tell us nothing about retrieval.

Matching Titan's 1024 dimensions to bge-m3's is **cosmetic**. The vectors are not
comparable and the dimension count does not make them so. Titan is chosen because
it is AWS's default path, which is the more honest thing to compare a hand-built
pipeline against, and the more transferable thing to learn.

Both are immutable in place. Changing chunking replaces the `data_source`;
changing the `embedding_model` replaces the whole `knowledge_base`. Terraform
forces the replacement rather than letting it drift, which is the same property
`collection_name` gives project 01.

## Interfaces

New modules, each with one job:

- **`parameters.py`** — reads the committed SSM paths, returns a plain mapping.
  The only module that touches SSM, so "config does no I/O" stays checkable by
  reading imports. Its own tests, with SSM mocked.
- **`config.py`** — `load_config(env: Mapping)` keeps project 01's shape and
  stays pure. Its tests stay pure. Raises on a missing value, naming the path.
- **`kb_client.py`** — `Retrieve`, and the `ingestion_job` operations.
- **`answerer.py`** — `Converse` plus the `v1` prompt.
- **`rag_query.py`** — the traced pass; returns answer and usage.
- **`main.py`** — the CLI, composing the above. No logic of its own.

**Ingestion exposes `start` and `status` as separate operations** from the
outset. The CLI composes them into a blocking `ingest`; the API in slice 7 will
start a job and return its id, with status as a second endpoint. One component,
two callers, no logic in either — the reason project 01 keeps its logic in
components rather than inside the terminal command.

`ingest` records the job statistics on every run and **exits non-zero when
`numberOfDocumentsFailed > 0`**, printing `failureReasons`. Bedrock silently
skips documents it cannot handle and still reports success, so an un-ingested
file would otherwise look exactly like a retrieval-quality problem. This mirrors
what `verify-corpus` already does for project 01's corpus.

A `Retrieve` before an `ingestion_job` finishes returns **empty, not an error**.
Whatever reports results must keep "not finished" distinguishable from "nothing
found" — the same class of trap as a `trace` reading zero tokens because it was
not ready.

## Done

**Slice 3 is a measurement, not a gate.** Every previous evaluation in this repo
decided whether something shipped; reranking was switched off at 0.720 against a
bar of 0.780. Project 02 has nothing to ship or not ship. No result halts it, and
slices 4 onward proceed whether the numbers are better or worse.

**One tripwire, fixed in advance.** If `evidence_found` lands below **0.44** —
half of project 01's 0.880 — treat it as a setup fault, not a finding.
Investigate the ingestion statistics, the chunk character distribution, the
retrieval configuration and whether ingestion had completed, **before** recording
any conclusion. The point is to avoid writing "managed RAG is worse" into the
roadmap when the real cause was a silently skipped document or a bad token
translation.

## Open questions

Deliberately deferred, each its own experiment, one variable at a time:

- **Chunking strategy** — `semantic` and `hierarchical`, versus `FIXED_SIZE`.
  Each needs a new `data_source` and a fresh `ingestion_job`.
- **`embedding_model`** — Cohere Embed v4 versus Titan V2. Needs a whole new
  `knowledge_base`; the expensive rung.
- **Answering model** — Nova Lite versus Haiku 4.5.

Genuinely unknown:

- **What `numberOfDocumentsSkipped` counts.** Unchanged files on a re-run, or
  only problem files. If the former, gating on it would fail every re-run. Left
  open until the first real `ingestion_job` shows which it is.
- **Where the `v1` prompt text lives** — copied into project 02, or promoted to
  `shared/` beside the evaluators. A slice 3 decision; project 01's registry
  freezes old prompt names so recorded experiments stay reproducible, and sharing
  the registry across projects has to not break that.
